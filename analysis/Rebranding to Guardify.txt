3. Signing, distribution, and security-sensitive items
Signing: current artifact is self-signed v2-only (CN=Paresh Joshi, cert SHA-256 f938…8dbd, valid 2011–2038) — custom/enterprise style, not Play App Signing lineage (§2). A Guardify release needs a deliberate keystore strategy: retain key for in-place updates to this build, or use a new Guardify key (new install identity). Do not ship with debug leftovers like xanadu_debug=true (§3.4, §8.4).
Exported surface to review during rebrand: 7 exported ContentProviders guarded by signature-level permission (verify its protectionLevel, not recovered), exported receivers/services including AutoStartKpReceiver and RemoteLockIntentService exported without permission (§3.2, §8.2, §8.7). Rebrand is an opportunity to tighten these.
Manifest posture: persistent=true, boot receivers, sticky/re-delivered foreground service, DnsVpnService, accessibility/device-admin bindings are core to enforcement (§3.1, §4.3–§4.6) — renaming must preserve privileges/foreground types.
Cleartext & config: bundled http://kiddoware.com/... icon URLs imply network security exceptions; review @xml/network_security_config (not recovered in report) as part of domain migration (§8.6, §9).
4. Data, storage, and user migration
Local/Room schema: KidsApplication, User, Category, AppLaunches, tasks, scheduler, etc. (§6). Package/database/provider authority changes can invalidate local data unless migrations/authorities are preserved.
Defaults & flavor: default user/category seeding and BuildConfig.FLAVOR-derived values exist in startup logic (§4.2, §6) — set Guardify defaults/flavor explicitly.
Backups: local + Firestore cloud backup/restore flows (FirestoreBackupIntentService, CloudBackupActivity, etc.) are tied to current Firebase/backend (§4.8, §7).
